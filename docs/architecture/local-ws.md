# Local websocket

[Durable tasks](tasks.md) add `tasks.list`, `tasks.get`, `tasks.create`, `tasks.update`, and `tasks.run`. Bootstrap carries `tasks`, and `tasks.changed { task }` carries each persisted change. Mutations carry `request_id`; edits and runs also require `expected_revision`. A stale revision is an error. Remote task writes route to the task's fixed authority Runner through sealed `tasks.*` requests; `tasks.validate_run` and `tasks.finish_run` validate and settle the assigned Runner's run.

JSON on `ws://127.0.0.1:4862/ws`. Requests are `{ id, method, params }` and get `{ id, result }` or `{ id, error: { message } }`; events are `{ event, data }`.

Only local programs get in (`ws.rs`). A browser lets any page open a websocket to 127.0.0.1 and leaves the check to the server, so every route answers `403` to a request that carries an `Origin`, which a page's always does and the clients below never send, or whose `Host` is not `127.0.0.1:<port>` or `localhost:<port>`, as a DNS-rebound page's is not. The upgrade also takes `Authorization: Bearer <token>`, compared in constant time, or answers `401`. The token is `serve-token` in the CLI's data directory: `lorca serve` makes it once it holds the port and keeps it for later starts. Every client reads it there on each connection, so a CLI it starts and one it finds running (`lorca service`, another app) both take it: the desktop app (`client.go`) from `LORCA_HOME` or the build's default folder, the one they start the CLI with, and `lorca`'s commands that go through a running serve (`serve_call`) from their own, saying so when the serve on the port keeps another folder. `/` answers `lorca`, for a check that the port answers, and nothing else.

Routines take an IANA `timezone` and a `missed_run_policy` (`coalesce` or `skip`) on `routines.create` and `routines.update`, and `routines.describe { schedule, timezone?, missed_run_policy? }` checks both. A routine on the wire carries its `health` and a derived `state` ([Routines](routines.md)). `device.service_status { id? }` answers `{ installed, running }` for this CLI's service, or another Runner's through the sealed `service.status` request.

`handoffs.list/get/follow_up/cancel/report` inspect and manage durable delegated work through the same local API. Their request and report shapes, source-chat destination and per-attempt job comparison are described in [Handoffs](handoffs.md#inspection-follow-up-and-recovery).

Workflows add `workflows.start` / `workflows.get` / `workflows.configure` / `workflows.connection` / `workflows.sample` / `workflows.review` / `workflows.enable` / `workflows.cancel`, each answering the setup's view; `marketplace` answers `packs` beside `plugins` and `bots`. The roster's optional `workflows` array carries the setups, merged one by one, and a sample is a `workflow_sample` job on the existing sealed job path: [Workflow onboarding](workflows.md).

The app may choose ids (`bots.create.id`, `chats.create.id`, `chats.send.message_id`) so its optimistic rows match the CLI’s events.

[Bot templates](templates.md) use `templates.contents`, `templates.export.preview` / `templates.export`, `templates.share` / `templates.unshare` for links, and `templates.import.preview` / `templates.import`, which take a `path` or a `link`. The final operations take `reviewed: true` and the preview's `expected_digest`, and refuse contents that changed since. File paths belong to the local CLI. The snapshot and `roster.changed` carry the account's `shared_links`, which the roster blob holds with their keys.

`routines.create` takes an optional `check` only on the bot's own Runner; a template import creates its routines there. `routines.create` also takes `receiver` and `subject`, and both take `calendar` and `event_match`, which only the bot's Runner can set up; a routine on the wire carries `once_at`, `events`, or `calendar` for the apps to word, `routines.regenerate_key` makes a webhook's new key, `routines.subscribe` has a routine waiting on setup try again, and `receivers.setup { receiver, subject? }` answers a receiver's setup link ([Routine triggers](routine-triggers.md)).

Skills are folders on a Runner, outside the snapshot and the roster: `skills.list` / `skills.get` / `skills.save` / `skills.remove` / `skills.export` / `skills.generate` read and change them, an edit or a removal carrying the folder's hash it read. The [Skills API](skills.md#app-and-api) defines the parameters and results. A Device that is not the bot's Runner sends each as a sealed request there. Each bot's and group's skill syncs as an account-encrypted `playbook` blob (`v: 2`, the folder as a zip) in a latest-only slot of its own, grouped under its group chat or its bot's DM.

[Workflow feedback](feedback.md) adds `feedback.list` / `feedback.record` / `feedback.propose` / `feedback.accept` / `feedback.reject` / `feedback.rollback` / `feedback.settings` / `feedback.exclude` / `feedback.review`, each answered by the bot's Runner, and `feedback.changed { bot_id, pending_count }` when a bot's feedback changes there; the app then reads the list again.

`outputs.publish { chat_id, bot_id, name, path? | url?, mime?, task_id?, replaces?, evidence? }` publishes on the producing Runner and returns `{ message, task_evidence }`. `outputs.list { chat_id, task_id? }` returns `{ outputs: [Message] }`, every version this Device has synced. Each output is a text/attachment message with additive `output` provenance, version and evidence metadata, delivered through the existing snapshots, message events and encrypted chat blobs. File bytes use the account-encrypted `file` transport. `files.path { attachment, named?: true }` fetches a file on any paired Device; `named` preserves its filename and extension for native handlers. See [Outputs and evidence](outputs.md) for fields, references and version rules.

What the apps get of a chat is a view of the message rows in `lorca.sqlite3` (`LocalStore::page`, then `Message::for_app`). A snapshot queries each chat's newest 60 messages and sets `has_more` when older rows remain; `chats.messages { chat_id, before?, limit? }` queries the page before a message id, oldest first, with `has_more`. The macOS transcript asks for it as it scrolls within reach of the first row and holds what is on screen in place; the phone asks from FlashList's `onStartReached`. Both keep pages they loaded when a later snapshot arrives. A `tool` message reaches the apps, in snapshots, pages, and `message.*` events, with its name, summary, running state, the first 400 characters of its detail, and a command's `terminal`, and without its arguments and result: the apps show none of that, and a file read or a command's output runs to hundreds of kilobytes. Permission cards likewise omit their reviewed argument payload. A Runner's database keeps the complete rows for later model context and permission handling. The no-Runner mobile core persists only `Message::for_app()` for these rows, so a phone never stores the full arguments or tool result it cannot use.
