# Outputs and evidence

A bot publishes a generated file or an existing HTTPS document link with `publish_output`. An output is a completed text message with additive `Message.output` metadata; its file stays in the message's `attachments`, and its text says what the transcript shows. The producing bot and chat come from the turn's bound context. Every paired Device reads the same record through encrypted chat sync, and clients that render text and attachments show the deliverable too.

## Publishing

`crates/cli/src/outputs.rs` owns the publication helper, output metadata, evidence, immutable references, and the bot tool. The tool is available directly and in codemode as `tools.publish_output`. Its arguments are:

```json
{
  "name": "Verification.txt",
  "path": "results/tests.txt",
  "task_id": "task-3a249410-8034-4be2-bf42-9e68b4fe2c41",
  "evidence": {
    "kind": "test_result",
    "summary": "The focused tests pass.",
    "status": "passed",
    "command": "cargo test -p lorca outputs::tests --lib",
    "exit_code": 0
  }
}
```

Exactly one of `path` and `url` is required. A relative path resolves in the producing bot's working directory; `mime` overrides the filename's media type. Publication runs on that bot's assigned Runner and requires membership in the chat and an account key. A file also needs the bot's [Access](bot-permissions.md#execution-boundary) to allow reading files; without it the call is refused and the user is asked, as for `read`. Files are regular files up to 100 MiB, copied into the private attachment store with a fresh attachment id. The file blob is encrypted with the account DEK and queued before the chat message. The source path stays on the Runner. A changed or removed source file does not change the published copy.

A `url` is an HTTPS document reference without embedded credentials. Recording it performs no request to the document's service. Creating a document, uploading bytes, or publishing externally uses the existing shell or plugin tools and their [Auto-review boundary](auto-review.md). Integrations and their credentials stay on the assigned Runner.

The local API is `outputs.publish { chat_id, bot_id, ...arguments }`, on the producing Runner, and `outputs.list { chat_id, task_id? }`, on any paired Device. Publish returns `{ message, task_evidence }`. List returns `{ outputs: [Message] }` in transcript order: every version this Device has synced. A SQL query selects output rows without materializing unrelated tool results.

## Versions and references

`Message.output` carries `id`, `name`, `mime`, `bot_id`, `chat_id`, optional `task_id`, `version`, optional `previous_message_id`, optional `url`, and optional `evidence`. The stable `out-UUID` id identifies a deliverable's series. Each version has its own immutable message id and, for files, its own attachment id.

Passing `replaces: <previous message id>` publishes a new version. It keeps the series id, producing bot, chat and task, increments `version`, and retains the preceding message and bytes. Publication is serialized on the producing Runner; a stale predecessor or a predecessor from another scope is refused. The encrypted outbox and relay have separate message slots for every version, so superseding a streamed message does not discard output history. Chat deletion uses the existing group deletion to remove its output messages and file blobs together.

The shared reference is `{ chat_id, message_id, output_id, version }` (`OutputReference`). `Output::task_evidence(message_id)` supplies `{ kind: "output", label, ...reference }`, an immutable task evidence reference. `task_id` uses canonical `task-UUID` ids. Outputs store references to tasks and introduce no task records. The bot tool returns the reference as text and as structured codemode output, alongside its metadata.

## Verification evidence

`evidence` carries `kind`, `summary`, `status`, optional `command`, and optional `exit_code`. Kinds are `test_result`, `before_screenshot`, `after_screenshot`, and `verification`; statuses are `passed`, `failed`, and `unverified`. A nonzero exit code conflicts with `passed`; zero conflicts with `failed`. A local screenshot requires an image with PNG, JPEG, GIF, or WebP dimensions. Tests and visual work retain their logs, reports, and before/after files as output versions. The turn prompt directs bots to publish this evidence and describe remaining uncertainty.

A [coding agent](coding-agents.md#when-it-is-done) a bot runs leaves its work the same way, as its bot's outputs each time it is done: its diff, the pull request it names, and the files it saved as proof, its evidence `unverified`.

Evidence reports the producing bot's verification claim; storing a result does not execute a check or mark a task complete. The record retains its canonical task reference and immutable output version; task completion is a separate operation. Later turns fetch published file attachments and materialize them into the reading bot's workspace, with provenance and version ids in model context, so a teammate can inspect the underlying result.

## Retrieving and inspecting

`files.path { attachment, named?: true }` fetches missing bytes from the relay, opens them under the account DEK, and returns a local path. The optional named copy is private and keeps the original extension under `files/open/<attachment id>/<safe name>`, so the system's handlers recognize reports and recordings. Attachment ids are checked before resolving paths. An absent relay blob returns a clear unavailable-file error; a user can retry after connectivity or an upload recovers.

The CLI also writes the output into the message's text, in English (`outputs::message_text`): the link, and what the bot checked (`Test result · Passed: All 23 links answer.` with the command as inline code), for clients that show only text. Every app draws a bot's output in the transcript as a card of its own, without a bubble or a time (`outputCard` in the desktop app's `chat.go`, `OutputCard` in the phone's `src/ui/outputs.tsx`), from `Message.output` rather than that text: an icon tinted for the kind of file (`kind`: code, data, table, archive, image, video, audio, PDF, text, or a link, from the file's extension and then its media type), the name, and the type and size (`HTML · 18 KB`, or the link's host). The apps show the file, not what the bot says it checked: `Message.output.evidence` stays in the record for tasks and later turns, and no app draws it. Its card is rounded, with the file's icon, the name, and the type and size beside it; a link has its symbol on a tinted tile. Every file in the desktop app, on a card, in a bubble, in the inspector, and in the viewer, shows as Untitled UI's solid file icon (`fileicons.go`, `assets/fileicons`, from the MIT-licensed `@untitledui/file-icons`): a page in the format's color with its extension on it for the 40 formats it has, and its kind's page (code, a document, a picture, a recording, a table, or a blank page) for the rest, by extension and then media type. A lone card of a Markdown, HTML, CSV or TSV, or text file shows the start of the file above that row as a page rising from a ground tinted for its kind and fading out before the row (`outputPeek` in `chat.go`, `peek.go`: a Markdown file's first heading and paragraph, an HTML page's `<title>` and first `<h1>` in a small browser window, a table's first five rows and four columns, other text's first seven lines in the monospaced font), read once per file, at most 8 KB, off the main thread. A picture there is not a card but the picture itself, whole, (`imageOutput`), and opens in the file viewer. The phone's card has an image's preview (the top of a tall one, at most 200 pt). A run of one bot's outputs with nothing between them, such as the proof files a coding agent saved, is compact: a row each, without a peek or a preview. On the desktop the run is a column of separate cards a few points apart, with a picture standing apart from it; on the phone it joins into one list of rows, each with the icon (an image's own picture, as a thumbnail), rounded only at its ends, and in a group the bot's avatar sits beside its last row. Each app marks an output's place in the run when it builds the transcript's rows (`outputStack` in `chat.go`, `stackAbove`/`stackBelow` on the phone). A click opens the output's viewer or screen; a file that could not be fetched says so and is fetched again on a click. The desktop app also lists a chat's outputs in the inspector, the latest three with View all, and opens each file in a viewer that covers the window (an image, Markdown, an HTML page, a PDF, or text) with every version and the file's facts in a pane at its side, Open, and Save As… ([The desktop viewer](#the-desktop-viewer)); the phone lists them in a chat's Details and opens each in a screen with Open and Share… ([Phone app](phone-app.md)), fetching the file through its own core like any other Device. The apps get every file through the local CLI, ask for the named copy only to open or save it, and keep a failed fetch's reason until the user retries. An HTTPS document link opens only when the user opens it.

## The desktop viewer

`outputs.go` and `model/outputs.go` in `desktop/`: the inspector's Outputs section, hidden while the chat has none, shows the three latest outputs with each one's size, and View all; a row opens a file output in the viewer and a link output in a sheet with the link and the versions. The viewer (`viewer.go`, kinds from `model.PreviewKindOf`: the extension, then the media type) is also what a file in a chat, a picture included, opens on a click (`presentFile`; the tile's menu keeps Open and Save As…). It covers the whole window as a full-window sheet (`presentFullWindow` in `overlay.go`: no scrim, no outside to press): a 52-DIP bar that is the window's title bar, dragging the window and clear of its controls, with the file's icon, its name, and what it is (`PNG · 640 × 360 · 4 KB`, or for an output its bot, day, and size); Preview and Source in its middle for Markdown, HTML, tables, and SVG; and Copy for text, Save As…, Open, and Close at its end. Escape and Close put it away, Open hands the file to its app and closes it, and a file that could not be fetched says why with Try Again. It opens from a little smaller and lower on a spring,. An output's viewer has a 320-DIP info pane at its side, toggled by Show Info and Hide Info and open to start with when there is more than one version: the versions newest first on a line of stops, the one on screen filled, each with its day and its file's size, a click putting it on screen; and the file's kind, size, dimensions, bot, and day. A link output's sheet shows the same versions. A published picture shows in the transcript as the picture itself, whole, up to 360 DIPs on a side, with no name or size (`imageOutput` in `chat.go`), and stands apart from the run of file outputs around it. A picture in the viewer (`picture.go`) is fitted to the window on the `Window` ground of the appearance. It is a page in a `ui.WebView`, since MyGo's native views hear the wheel but no pinch: two fingers pinch it larger and slide it about, Ctrl or ⌘ with the wheel zooms, a drag moves it, a double click zooms in and back, and `+`, `-`, and `0` zoom and fit. The page gets the picture as a data address (up to 32 MiB) under the preview origin, and asks to close by navigating to its `/close`, which `previewNavigation` turns into a close of the viewer, since the web view takes the keyboard from it. With no web view, or for a larger picture, the viewer shows it fitted, as a native image. Under the bar the file runs edge to edge: a CSV or TSV file as a grid (`encoding/csv`, up to 1,000 rows) with its first row as a header that stays while the rows scroll and a number before each row; an SVG drawn by the web view as a picture is, or natively where there is none; a recording (MP3, WAV, M4A, AAC, FLAC, Ogg, MP4, MOV, M4V, WebM) played by the web view from the CLI's named copy; a JSON file on one line laid out with indents; Markdown drawn as a page in a 760-DIP reading column (up to 1 MiB; `markdownOptions.Document`: 15 DIP text on roomier lines, headings that step down from 1.9 times the body to its size, a quote on a tinted ground, a hairline rule, tables in a frame with a tinted header), an HTML page and a PDF filling a `ui.WebView`, code, data, and a document's source, up to 256 KB, in the monospaced font, unwrapped beside a column of line numbers that stays while the lines scroll sideways, other text wrapped in a reading column, each with a note under it of how much shows, and any other file as a card with its icon, name, and Open. Files are read off the main thread, and a file that is not UTF-8 text shows as a file card. An HTML page is loaded from its text under an https origin the app does not trust (`previewOrigin`), so it runs its scripts but cannot call the app's Go methods, which the app does not bind to pages anyway; `previewNavigation` cancels every navigation but the page's own anchors and opens a clicked web or mail link in the browser. A page larger than 1 MiB, or any HTML where no web view can be made, shows as source. A PDF loads from the CLI's named copy as a `file:` address in the web view on macOS and Windows; on Linux, where WebKitGTK has no PDF viewer, it shows as a file card, and Open hands it to the system. The viewer's web views are made off the main thread when first shown and destroyed when it closes. The demo (`LORCA_MOCK=1`) has Researcher's chat publish six files (`model/mockfiles.go`: Markdown, an HTML page with a script and a link, a PDF, a diagram, a long log, and a 1600 by 1000 chart on a fine grid, a picture of its own to pinch and slide) and carry a picture the user sent; the store finds them in a temporary folder as it finds the CLI's files. `Store.Outputs` lists a shown chat's outputs once and follows message events. Open and Save As… ask the CLI for the file under its own name (`files.path` with `named: true`); Save As… writes through a temporary file beside the destination, so a failed copy leaves what was there. In the transcript an output is a card of its own (`outputCard` in `chat.go`).
