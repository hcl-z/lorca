# Desktop updates and builds

How the [desktop app](desktop-app.md) updates itself, and how it is developed, tested, and built for each platform.

## Updates

`updater.go` uses MyGo's updater plugin. It checks once a day in the background, and a window of its own shows a new version's release notes with Install Update, Remind Me Later, and Skip This Version, the download's progress, and the offer to relaunch. It installs releases signed with the update key, as a delta from the running version when the release has one, and keeps the user's choices in `updater.json` in the app's data directory. **Check for Updates…** opens that window, and General has the version, the last check, and switches for automatic checks and automatic installs, which follow the plugin's changes (`updater.OnChange` redraws the windows). The window speaks the language picked in Settings, else the system's; a new pick reaches it at the next launch. Its releases are this repo's, tagged `desktop-vX.Y.Z` (`updates` in `mygo.config.ts`, with the public key). The repo's latest release stays the CLI's, so release builds find the newest `desktop-v` release through the GitHub API (MyGo's `tagPrefix`), and read its update manifests. `bun run release-desktop` uploads to a draft of the version through `go tool mygo build -upload`, here or in the Release CLI and desktop workflow (`.github/workflows/release-cli-desktop.yml`), which `bun run release --push` or a run by hand starts on `main`: it drafts the release with the changelog's section and builds Windows x64, Linux x64, and Linux arm64 side by side on Ubuntu and macOS arm64 on a Mac runner, which signs it ad hoc and makes its disk image, and publishing the draft, without making it the latest release, releases the update. The app has its own version, `version` in `desktop/mygo.config.ts`, apart from the Mac app's, and its own release notes, the version's section of `desktop/CHANGELOG.md`: [docs/releasing-desktop.md](../releasing-desktop.md). A build that cannot write where it is installed, `mygo dev`'s or the Debian package's in `/opt`, leaves the menu item and the General rows out.

## Development and builds

`bun run desktop` builds the CLI and runs `go tool mygo dev` (Lorca Dev, `app.lorca.dev`, with `~/.lorca-dev` and port 4863), which rebuilds and relaunches the app on a Go change; `LORCA_MOCK=1` runs the demo instead of the CLI, and `LORCA_PORT` points the app at a CLI on another port. `go tool mygo vet .` in `desktop/` runs Go vet and checks for build values stored in state or captured by workers. `go test ./...` (slow; how to run a part of it: [Testing the desktop app](development.md#testing-the-desktop-app)) runs the model's tests and the views' tests, which build the windows over the demo's store in MyGo's offscreen tester (`ui.NewTester`), click and type into them, and check what they show; with `LORCA_RENDER=<folder>` they also write each frame they look at as a PNG. `LORCA_E2E_PORT=<port> LORCA_E2E_SERVER=<base URL>` adds `TestE2EAgainstCLI`, which drives the main window over a CLI with an identity on that port: it adds an OpenAI-compatible server at that URL as a custom provider through its sheet, runs the first bot on it, and checks the reply that streams back. `bun run desktop:build [platforms]` builds the CLI for each platform into `desktop/resources/<goos>-<goarch>/bin` (static musl builds for Linux, with cargo-zigbuild, as the CLI releases are; cargo on a Mac for macOS) and runs `go tool mygo build -platform`; MyGo needs no cgo, so Windows and Linux build from any computer, while `darwin/arm64` builds on a Mac, which links its CLI, signs the app, and makes the disk image. A Mac builds macOS on Apple silicon and Windows and Linux on x86-64 by default. `mygo.config.ts` signs the macOS app ad hoc unless `SIGN_IDENTITY` names an identity, and notarizes it with the notarytool profile `NOTARY_PROFILE` (in the keychain `NOTARY_KEYCHAIN`) only when that is set; releases set neither.
