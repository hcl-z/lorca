# Handoffs

`crates/cli/src/handoffs.rs` owns durable bot delegation. A handoff is a request and its attempts, with a stable `handoff-<UUID>` id. Each attempt has a new job id, the requesting bot and chat, the source Runner, the job it belongs to (`origin_job_id`, which a [Stop](stopping.md#what-the-turn-handed-off) reaches), an optional canonical parent `task_id`, the recipient bot, its DM and Runner, the message and supplied context, expected output, acceptance criteria, hop count, and creation time. The destination for reports is the requesting bot's source chat. Task ids and output versions are references to their owning records.

## Admission and delivery

`message_bot { bot_id, message, context?, expected_output?, acceptance_criteria?, task_id? }` creates the contract and returns `handoff_id`, `job_id`, `target_runner_id`, and its delivery state. `task_id` defaults to the requesting turn's task and must name a [durable task](tasks.md) this Device has. A bot cannot delegate to itself or a member of its current group; the eight-hop limit also applies to handoffs.

The CLI encrypts the handoff's local record with the account DEK and stores it as a binary ciphertext in SQLite's `handoffs` table. The contract's encrypted `handoff` relay update and a remote Runner's sealed `job` envelope enter the outbox in the same transaction as the record. A local recipient starts through the same job lifecycle. `admit` writes both chats' markers with the request, for a first attempt and a follow-up alike. The requesting chat gets "Messaged ◉ Name" (`sent-<trigger message id>`, authored by the requester, a `Body::Handoff` from the requester to a bot outside the chat), so the sender sees the hand-off whether or not its tool call finished; the same marker keeps a resumed attempt from drawing a second one. The recipient's DM gets the "Message from ◉ Name" marker with the request: the message, then the supplied context, expected output, and acceptance criteria under their own headings, without ids. `Job.handoff` carries the complete contract, and the recipient's system prompt carries it again on every turn of the attempt, so compaction never drops it; it says a teammate asked for the work, not the user. `Job.task_id` carries task context without claiming parent-task ownership or completion; the recipient's turn, and the requesting bot's continuation, count toward the task's [limits](budgets.md) instead of their chats'.

Delivery is `queued_local` for this Runner, `queued_relay` when the relay reports the recipient Runner online, `waiting_for_runner` when it is offline, and `waiting_for_relay` when this Device has no relay configured. These queue states describe admission, not execution. A Runner claim changes the view to `running`; a terminal report changes it to `finished`. A relay serving protocol 3 accepts the handoff kind. A relay older than that refuses it, and the Device drops the refused blob as it drops any other, so the rest of its outbox keeps syncing; the job envelope still carries the whole request, but reports between Runners reach the requesting Device only through an upgraded relay. The handoff remains inspectable indefinitely, including while an offline Runner's job waits on the relay; the ordinary five-minute remote-turn display timeout does not expire it.

## Reports and continuation

The recipient can call `handoffs { action: report, status: completed | failed | blocked | cancelled, summary, result_links?, evidence? }`. The tool binds the handoff and active job to this turn, ends the delegated turn, and returns the saved report. The summary is one or two sentences for the requesting bot, in the language the bot uses with the user. A report can add textual evidence and structured references in the canonical task-evidence shape: `kind`, `label`, and the relevant chat/message, file attachment, HTTPS URL, output id/version, or review id. An output version is `{ kind: output, label, chat_id, message_id, output_id, version }`; its message id names the immutable version. Link validation checks the reference shape, not an independent review of its contents. The Runner adds its own links to what the turn said and its observed tool outcomes to the evidence.

The Runner reports on its own when the turn ends without an explicit report, from the turn's outcome (`automatic_report`). A turn that replied produces `completed` with its last reply as the summary and a link to that reply; one that said nothing but published an [output](outputs.md) produces `completed` too ("Published report.pdf."); a turn that failed or never ran produces `failed` ("Couldn't finish: …") with the error or the notice that said why (a missing provider, say), and an agent loop that failed outside a model reply posts that notice itself, so the reason always reaches the report; a turn that ended with neither produces `blocked`, and a hard Stop produces `cancelled` ("Stopped before finishing."). A notice posted on the way, such as a compaction, changes nothing. A turn its limits (or its task's) stopped, its runtime limit included, reports `blocked` with the limit's reason, and resuming it in Limits sends the same request again as the handoff's next attempt (`handoffs::resume_stopped`), with no second marker in the recipient's DM, since the stopped attempt has reported and a report never changes. Evidence names observed tool outcomes and their message ids; an [output](outputs.md) version the turn published (`Message.output`) becomes an `output` link to that version. Completion is the recipient's claim. The requesting bot reads the report and checks the acceptance criteria before completing a parent task.

A recipient whose turn hands part of the work on with `message_bot` reports once that work is done, not when its first turn ends. A delegated turn that ends with handoffs it made for this work still unsettled (`outstanding_downstream`: no terminal report yet, or one whose continuation has yet to run on this Runner) publishes a running report ("Waiting on Writer") and keeps their ids on the attempt (`waiting_on`). Each downstream report starts the recipient's `handoff_result` continuation, whose `origin_of` is the waiting attempt's job, so the continuation answers for it: its `handoffs` tool reports that attempt (`bound_request`), and its system prompt says its reply goes back to the requesting bot. When the continuation ends with nothing left outstanding, the attempt reports from it (`settle_waiting`), from what the recipient's DM holds since the attempt began; one that passes more on keeps it waiting. Cancelling or stopping a waiting attempt stops what it passed on (`stop_downstream`), and the eight-hop limit holds across the chain. A restart leaves a waiting attempt waiting, not failed, and settles it when what it waited on has reported with no continuation left to run.

A `handoff` update carries its request and can arrive before the request's own blob. Requests, Runner reports and requester cancellations have separate relay slots per attempt, all encrypted with the account DEK. A terminal Runner report supersedes its running claim. A cancellation is a separate sticky record and wins a concurrent finish. A late report merges into its original attempt and cannot replace a later follow-up.

The source Runner adds a deterministic report message (`report-<request job id>`) to the source chat and starts a deterministic `handoff_result` job for the requesting bot. The message is a `Body::Handoff` from the recipient to the requesting bot whose text is the summary: every app draws it as the "Message from ◉ Name · first line" marker, which opens the whole summary on a click, in a DM and in a group the recipient is not in, and the requesting bot reads it as "[Message from Name]". The continuation's system prompt carries the rest: the status, result links, and evidence as JSON, and what the bot asked for, so it continues the work without waiting for another message from the specialist. A `blocked` or `failed` report becomes a quiet [attention](attention.md) blocker ("Scout couldn’t finish") only after that continuation has read it and left the work stuck, with no follow-up or cancellation, or at once when there is no continuation to run; a follow-up or cancellation settles it. A requester's own cancellation posts no report and starts no continuation. A stopped attempt, whether the user stopped the recipient's turn or the turn that handed it off ([Stop](stopping.md)), posts its report and starts no continuation: the requesting bot reads it in its next turn. For a task's handoff, the report message also joins the task's evidence through the task's own revision check (`tasks.update`, retried once on a conflict), as a reviewed action's outcome does, when the task links the requesting chat. Duplicate updates preserve one report message and one continuation. Other paired Devices keep the encrypted handoff state and receive the ordinary encrypted chat message.

## Inspection, follow-up and recovery

The `handoffs` tool offers `list`, `get`, `follow_up`, `cancel`, and `report`. It scopes inspection to handoffs where the bot is a participant. Other turns' system prompts say nothing about handoffs, so they stay the same from turn to turn. The local API offers:

- `handoffs.list { bot_id?, chat_id?, task_id?, outstanding? }` — locally synced records, including blocked work when `outstanding` is true.
- `handoffs.get { handoff_id }` — the current contract, delivery, report, and attempt history.
- `handoffs.follow_up { bot_id, handoff_id, job_id, message, origin_job_id? }` — the requesting bot retries a terminal attempt with more instructions, retaining context, output contract and criteria; the tool sends its turn's origin, else the attempt keeps the last one's.
- `handoffs.cancel { bot_id, handoff_id, job_id, reason }` — the requesting bot cancels the attempt and queues a sealed `job_cancel` for a remote recipient.
- `handoffs.report { bot_id, handoff_id, job_id, status, summary, result_links?, evidence? }` — the recipient reports its current attempt.

Mutations run on the bound bot's Runner. Follow-up and cancellation compare the supplied job id under the handoff lock, so stale inspections cannot replace newer work. A still-running attempt is cancelled before it is replaced. Inspection reads local synced state on every paired Device, including after a restart.

A queued local job is recorded before it waits for the chat lock. Execution claims are encrypted before effects start; duplicate envelopes cannot execute an already claimed, finished, cancelled, or superseded attempt. Startup (`runtime::resume_sent_jobs`) resumes queued local handoff work and pending result delivery. A claim left running by the previous process, other than one waiting on work it passed on, becomes a failure ("Stopped when Lorca restarted on its Runner.") with interruption evidence; the Runner leaves effects for explicit inspection and follow-up. A coordinator continuation interrupted after its claim is not run again, like any turn a restart cuts off; its report stays in the chat. Terminal reports, their report messages and continuation state survive restarts.
