# Phone app

`mobile/` is an Expo app (React Native, expo-router, TypeScript) for iOS and Android. A phone is a Device and never a Runner, and it links the same Device core the CLI is built from rather than porting it: `crates/mobile` (`lorca-mobile`) wraps the `lorca` library, built without the `runner` and `server` features, in a UniFFI object with three calls, and `mobile/modules/lorca-core` is the Expo native module around it.

- **The core** (`crates/mobile/src/lib.rs`): `Core.start(home, name, os, osVersion, model, listener)` loads the App from the app's own folder, sets the host facts (a phone cannot probe them), and starts the relay sync loop on an embedded tokio runtime; `request(method, params)` is one call of the JSON API in `crates/cli/src/api.rs`, blocking on the module's background queue, answering `{ result }` or `{ error: { message } }`; `wake()` asks the relay again now (the app calls it on foreground, since the sync socket may have died while iOS suspended the app). Every event on the App's bus reaches the listener as the `{ event, data }` frame the websocket carries.
- **The native module** (`mobile/modules/lorca-core`, picked up by Expo autolinking): a Swift `Module` and a Kotlin one, each about forty lines, forwarding `start`, `request`, and `wake` and turning the listener's frames into a `sendEvent`. `bun run core` (`build.ts`) builds the Rust for `aarch64-apple-ios` and the simulator into an xcframework with the UniFFI Swift beside it, and for `arm64-v8a` and `x86_64` with `cargo ndk` into `jniLibs` with the Kotlin (over JNA). The built pieces are gitignored; a Rust change needs `bun run core` and a native rebuild, a JS change is a Metro reload.
- **The JS side** (`mobile/src/core`): `engine.ts` starts the core, mirrors its events into the zustand store (`store.ts`, the way the desktop app's store mirrors the CLI: `snapshot`, `roster.changed`, `message.*`, `job.*`, `chat.usage`, `relay.status`, `identity.changed`; events that arrive while a `bootstrap` snapshot is on its way wait and apply after it, as in the macOS app, so a snapshot built before the relay connected cannot undo that `relay.status`), and offers the screens the same verbs the macOS app has, each one request (`chats.send`, `bots.create`, `bots.update`, `pair.accept`, `providers.connect_*`, `providers.list_models`, `providers.api_key`, `providers.disconnect`, `device.set_name`, `device.unpair`, `device.update`, `identity.forget`, `sync.wake`, …). `prefs.ts` keeps the one thing that is the phone's own, the dictation language. Nothing about the account is stored outside the core's folder.
- **Pairing**: the phone scans the QR code the desktop app shows, pastes a string from the app or `lorca pair` on another computer, or opens it as a `lorca://pair?…` link; `pair.accept` does the handshake in the core and the first `bootstrap` snapshot fills the store.
- **Relay status**: the chat list's title slot (`src/ui/ChatsScreen.tsx`) stays empty while the relay connects, and speaks once that has taken a second, or four after the app comes to the foreground, when the socket the suspension killed is replaced: "Connecting…" with a spinner, or, once a try has failed (`relayError`), "Can’t connect" or, for an unknown machine, "Pair this phone again" beside a warning glyph. A tap on those opens an alert with the error (`src/ui/relay.ts`) and Try Now (a wake) or Unpair This Phone. "Update Lorca to sync" takes the slot over all of them. Settings › Account › Relay shows the error in place of "Connecting…".
- **Attachments**: the composer's `+` offers the photo library, the camera, and the file picker, and an image pasted into the field attaches too: `ImagePasteView` (`lorca-core`) around the field offers Paste for a pasteboard image on iOS through `RCTUITextView`'s replaced `paste:`, text with it still pasting, and on Android takes clipboard, keyboard, and dropped images through an `OnReceiveContentListener`; each lands in a cache file (iOS turns HEIC and TIFF into JPEG). A picked or pasted file's path goes with `chats.send`, and the core copies, encrypts, and uploads it as a `file` blob ahead of the message. A bubble that shows an attachment this phone does not have asks `files.path`, which fetches the blob and answers with the file; a fetch that failed says Couldn't download · Retry and is asked again only on a tap (`fileErrors` in the store). Images render as thumbnails sized from the width and height in the message; other files as a card with the file's icon, name, and size. A tap on either opens the file viewer (`app/file/[id].tsx`, after the desktop app's): full screen, the file's icon, name, and what it is in the bar, and the file edge to edge under it. A picture or an SVG pinches and zooms; Markdown is drawn as a page by the native Markdown view; a CSV or TSV file is a grid (up to 1,000 rows) with its header row kept in view and a number before each row; code and data run unwrapped beside line numbers, and a JSON file on one line is laid out with indents; other text wraps. Text is read from the head of the file (`readHead` in `src/ui/files.tsx`, at most 256 KB, 1 MB for a document), and the viewer notes how much shows. Markdown, HTML, tables, and SVG switch between Preview and Source. An HTML page runs in the system's web view (`PageView` in `src/ui/PageView.tsx`, `react-native-webview`), loaded from its text under an https origin the app does not trust (`PREVIEW_ORIGIN`), with no bridge to the app, no cookies, and no file access; `previewNavigation` (`src/core/files.ts`) keeps it where it is, opening a web or mail link the user follows in the browser and cancelling every other navigation. A PDF draws there on iOS and a recording plays there on both platforms, each from the CLI's named copy. A PDF on Android, whose web view draws none, and any other file are a card with its icon and Open. Open is Quick Look on iOS (`previewFile` in the native module, a `QLPreviewController` over the app), which draws pages and plays recordings, and the share sheet on Android (`expo-sharing`); the bar's menu holds Open, Share…, Copy Text, and an output's versions. Files show as Untitled UI's solid file icons (`assets/fileicons`, MIT, the desktop app's set; `fileIconName` in `src/core/files.ts`), drawn by `expo-image`. Both take the file under its own name, the private named copy `files.path { named: true }` keeps.
- **Skills** (`app/chat-info/skill/[id].tsx`, `save-skill/[id].tsx`, `src/ui/skills.ts`): Details lists the bot's or the group's skills and opens each in its own screen; Add Skill writes one or saves one from the chat's messages, drafted on the bot's Runner; every call goes to that Runner. See [Skills](skills.md#app-and-api).
- **Project** (`app/chat-info/project/[id].tsx`, `src/ui/project.ts`): as in the desktop apps, a group's Details has a Project section right after its name and description, with the group's [project context](project-context.md#the-apps) (`useProject`, from `projects.get`, which Details asks for when it opens and again on `projects.changed`): a row per entry with its kind and its link's host, or who suggested it, an orange mark for two versions or a link that could not be opened, five rows before Show More, and Add to Project, a menu of the kinds, Link, and File (picked with the document picker and sent to `projects.asset`). A row slides in the entry's screen: Title, the text, and the Link with Check Now and when it was last checked in the footer, or the file, which opens in Quick Look; who saved it in a footer; Add, Save, Accept, or Keep This Version in the toolbar; Remove at the bottom; and the desktop apps' alert when another Device saved first.
- **Outputs** (`src/ui/outputs.tsx`, `app/chat-info/output/[id].tsx`, `app/chat-info/outputs/[id].tsx`): as in the desktop apps, a chat's Details has an Outputs section after its name and description, hidden while there is none: the three latest outputs (`useOutputs`, from the loaded messages and `outputs.list`, which Details asks for when it opens) with their size, and View All for the rest. A row slides in the output's screen inside the same sheet: a preview (the image, the first 256 KB of a text file, or the file's icon, name, and size; a tap opens it in the file viewer), who published it and when, the versions as a list to pick from with each one's size, and Open (Quick Look, or the link in the in-app browser) and Share… (the share sheet, where the phone saves a copy), or Try Again when the file could not be fetched. See [Outputs and evidence](outputs.md).
- **Tasks** (`app/chat-info/durable-task/[id].tsx`, `src/ui/durableTasks.tsx`; not the Running tasks of `app/tasks`, which are a chat's commands): Details has a Tasks section after the name and description, with the chat's [durable tasks](tasks.md#in-the-apps) from the snapshot and `tasks.changed` (`useDurableTasks`), what waits on the user first, five rows before Show More, and New Task. A row slides in the task's screen: its state, reason, result and evidence (an output opens on that version's screen), the step the state allows as a row in the tint color, the goal, owner, next step, and Done when as a form Save writes back, what it waits for, its links, and Cancel Task. The core sends each write to the task's authority Runner.
- **Limits**: Details' Runs with row and the Limits screen, in [Budgets](budgets.md#in-the-apps).
- **Review** (`app/chat-info/review/[id].tsx`, `src/ui/reviews.ts`, `src/core/reviewEdit.ts`): as in the desktop apps, Details has a Waiting for review section after the name and description while the chat's bots have something open ([Review queue](review-queue.md#in-the-apps)); a row pushes the review screen. Its header reads like the permission card ("Chef wants to run a command on Workbench", the rationale under it), then one field holds the command, the call's arguments, or the draft, the details follow, and Reject sits apart at the bottom. Approve is the toolbar's Done-style button; an edit goes up first as the next version. A call's arguments come from the core as its JSON text and go back the same way (`exactJson.ts`, `requestText` in the native module's JS), since `JSON.parse` would round an id past 2^53.
- **Templates** (`src/core/templates.ts`, `src/ui/TemplateShareScreen.tsx`, `app/template.tsx`): Details' Share as Template, Settings › Shared Links, and New Bot from Template, which `lorca://t/…` links open; see [Bot templates](templates.md#in-the-apps).
- **Secrets**: [the card and a Runner's list](secrets.md#in-the-apps).
- **Channels**: Details' section and the channel's screen, in [Channels](channels.md#in-the-apps).
- **Feedback** (`app/chat-info/feedback/[id].tsx`, `feedback-item.tsx`, `give-feedback/[id].tsx`, `src/core/feedback.ts`): a DM's Details has a Feedback section after Routines with the bot's suggested changes, All Feedback, and Give Feedback, which picks one of its replies, since a long press selects text ([Workflow feedback](feedback.md#in-the-apps)).
- **Workflows** (`app/workflows/`): New Workflow in the chat list's New menu lists the marketplace's [workflows](workflows.md#the-apps); a workflow's screen sets it up on a Runner, runs its sample, and offers its schedule.
- **Access** (`src/core/access.ts`, `src/ui/AccessScreen.tsx`, `app/chat-info/access/[id].tsx`, `access-plugin.tsx`): a DM's Details has an Access row after Description, and a "needs more access" card's Edit Access… opens the same screen; see [Bot permissions](bot-permissions.md#requests-to-the-user).
- **Named accounts** (`src/ui/AccountScreen.tsx`, `app/chat-info/account/[id].tsx`, `app/settings/account/[id].tsx`): a plugin's rows in Details and in a Device's Plugins name each [named account](integrations.md) (Gmail · Work) with its state in a word or two (`src/ui/plugins.ts`) and no description; a tap slides in the account's screen, the desktop apps' Account card: its Name, which `plugins.rename` keeps when editing ends, and its sign-in row (Signed in, Not signed in, Needs more access, Needs setup, Can’t connect with the server's reason in the footer), with Sign in or Sign in again and Sign out. Sign in sends `plugins.connect` to the Runner, and the page opens in the in-app browser as a card's does; the Runner keeps the tokens. Adding an account and its setup are left to a computer. Browser is not among the rows: it is one switch in the bot's Access ([Browser](browser.md#in-the-apps)). Any other plugin's row slides in the same screen with its state. Every plugin's screen ends with its [call limit](budgets.md#shared-connector-admission): Calls and At once as menus of the usual values (60 a minute, 4 at once), the Runner's own value shown when it is another, which `connector_limits.set` saves at once.
- **Dictation**: the primary disc is Dictate while the field is empty (a small microphone sits inside the field once there is text). While recording, the field shows Grok Bot's pill: a stop square, the elapsed time, and bars that follow the microphone, with Send still beside it. The words land in the field after whatever was typed when the user taps the square, or go out at once when the user taps Send. The recognizer (`expo-speech-recognition`) listens in the first of the phone's preferred languages it supports (`src/ui/dictation.ts`; a Chinese speaker on an English-region phone gets zh-CN), or the language chosen in Settings or by a long press on the microphone.
- **Notifications** (`src/core/push.ts`, `expo-notifications`): after pairing, and on every launch and foreground, the app asks for permission once, reads the native device token, and registers it with the relay through the core (`push.register { platform, token, environment }`). The Swift module writes the core's push key into the build's keychain group (`group.app.lorca` or `group.app.lorca.dev`) at start and on `identity.changed` or `account.key_changed` (removed with the account); the notification service extension is its own target, generated at prebuild by `@bacons/apple-targets` from `targets/notify`. A tap opens the chat, a reply in the chat on screen makes no banner, and opening a chat dismisses its notifications.
- **Releases and updates**: an unsigned `.ipa` on GitHub for iOS, installed by sideloading, and APKs on GitHub that the Android app installs itself, in [Phone releases and updates](phone-updates.md).
- **Turns**: sending is `chats.send`; the core admits a `turn` Job on the bot's Runner or a group room, exactly as any Runner's CLI does. When a direct turn already owns the chat, the Runner promotes the new user message as steering after the current model step and its tools settle, and a question the turn waits on is dismissed rather than waited for; the admitted Job then exits when it reaches the lock because that message was already handled. In a group, the current member settles and the newly admitted room takes over. The `job.started` / `job.finished` events drive the "is working" row and "Chef stopped without replying"; `job.thinking`, `job.retry`, and the running tool rows fill in what the bot is doing, which the core reads in the Runner's `machine` blob and the chat log. The row shows every turn in flight, whichever Device started it, and is back when the app is closed and opened again (see Working state in [the desktop app](desktop-app.md)). While a turn runs, the composer's disc is Stop (`chats.stop`, in [Stop](stopping.md)), or Stop beside Send once something is typed, which steers instead.

While something waits on the user, the chat list has an Attention button beside Settings (a tray on iOS, Material's inbox on Android). It opens `app/attention.tsx`, a form sheet after the desktop app's popover: each coordinator's latest brief (the bot, when, and Decision, Changed, and Next lines), then a grouped list of items, urgent first, each with its category's symbol, the title, the next action, and "Review · Launch copy". A tap opens the item's chat; a long press offers its other source chats and Mark as Resolved. The header's ⋯ menu holds the Briefs and Urgent Items notification switches and the coordinator (Automatic, or one bot); with nothing left the sheet says so. Bootstrap and `attention.changed` supply the list from the core (see [Coordinator attention](attention.md)).
