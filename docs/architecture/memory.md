# Memory

What a bot keeps between chats, where it lives, and what may write it.

## A bot's memory

Every bot keeps its own long-term memory on its Runner, in Grok Bot's shape of a curated profile over append-only logs, as plain markdown under `~/.lorca/memory/<bot id>/` (keyed by id, so a rename or a changed working directory never moves it; `crates/cli/src/memory.rs`). Memory sits outside the bot's working directory on purpose. `turns::memory_write_guard` refuses, as the `memory` check in a turn's trace, a `write` or `edit` that names a path in it and a shell command that is not read-only and names one: by absolute path, `~` or `$HOME`, a relative path from the working directory or from any folder the command `cd`s to, or `memory/` right after a variable it cannot expand (`$LORCA_HOME/memory`). The shell review checks the same again for a codemode script's commands, and a coding agent's commands and file edits are held to it too. `memory_update` and `profile_update` are therefore the only writers, so the guarantees below cannot be bypassed by a bot's own tools; this is a policy check on what a command names, not a sandbox. A bot whose memory still sits in `workspaces/<id>/` has it moved once on the first start, index and `memory/` tree each moved on its own (renamed, or copied then removed across volumes); a part that fails stays in place and is retried on the next start.

- `MEMORY.md` is the curated memory. Its first 200 lines or 24 KB, whichever cuts first, open in every turn, in the note after the transcript rather than in the system prompt, so a fact saved mid-turn does not invalidate the provider's cached prefix ([Turn context](turn-context.md#the-system-prompt)). Past that nothing loads, and the note tells the bot how much is cut off and asks it to consolidate. The bot writes it only through `memory_update`, one dated entry per call (`- 2026-09-17 · from your chat with the user · the user prefers short replies`), never a whole-file write, so two of its turns cannot clobber each other: `append` adds a fact (an exact duplicate is refused), `replace` rewrites one unique passage, `supersede` strikes the old entry through with a date and adds the new fact so the file shows what changed, `remove` deletes a passage and records it in `forgotten.md` so it is not quietly added back.
- `memory/<topic>.md` files hold longer notes the bot reads with `read` when it needs them; the memory note lists their names.
- `memory/log/YYYY-MM-DD.md` is the bot's diary: what happened, not what is true. The Runner appends one line per finished turn (`- 09:05 · in group "Standup" · said "Sent the three flagged invoices…" · used bash, edit`), and the bot adds events with `memory_log`. Logs are never loaded into a prompt; `recall` finds them.

A bot made from a [template](templates.md#import) gets a DM and the template's memories as its `MEMORY.md`.

## The write gate

Every write is atomic, goes through a credential scrubber first (API keys, AWS and GitHub tokens, bearer tokens, JWTs, private key blocks, `password: …` values become `«redacted N chars»`), and passes the gate in `crates/cli/src/memory_check.rs`. The gate refuses an entry that:

- is longer than 1,000 characters;
- holds hidden, zero-width, bidi, or tag characters, which can make text read differently than it is;
- reads like an instruction to the bot ("ignore previous", "system prompt", "you are now", 忽略之前的指令, 不要告诉用户);
- carries a prompt in a URL's query (`?prompt=`, `?instructions=`, `?q=`);
- holds what looks like a credential;
- opens with a date of its own, which the entry already carries;
- adds a fact the user removed (it is in `forgotten.md`), one a supersede struck through, or one already there, compared without bullet, date, source, case, or extra spaces.

`replace` and `supersede` check only the new words, since the passage they change is meant to be there. A refusal comes back as a message the bot can act on, not an error. Memory is bot-authored as often as person-authored, and a page a bot read must not be able to plant a line it follows every turn.

## Learning from a quiet chat

The memory flush runs only before a compaction, so a short chat that never grows long enough would teach the bot nothing. `crates/cli/src/memory_capture.rs` reads a bot's direct chat once it has been still for five minutes, or once eight of the user's messages have arrived since the last read, whichever comes first. Only direct chats are read: a group's facts belong to no one member, and a channel's conversation is somebody outside Lorca writing. Each read covers the finished messages since the last one, from the newest 40, with one model call and no tools that asks for facts as JSON, each with the user's words it rests on; a channel contact's message and a system notice stay out of the transcript, and the bot's replies are context, never evidence.

A proposal whose quote is not in what the user wrote is refused, and the rest go through the same gate. Each proposal has a structured `about` field: `person` for identity, location, language, role, and lasting preferences that every bot should know; `work` for a durable fact about this bot's own duties. Project decisions and goals belong in [shared project context](project-context.md), ongoing work in [tasks](tasks.md), and completed events in `memory_log`; none of those is user memory. No word list guesses the destination. A `person` fact goes to the Runner's [profile](#the-users-profile), which every bot there reads, and a `work` fact to the bot's `MEMORY.md`. A fact the model submits to the wrong tool is refused with the tool that belongs to it. A fact that replaces one memory or the profile already holds, named as the file has it, supersedes that entry where it is, so "我搬到杭州了" strikes "the user lives in Shanghai" through instead of sitting beside it; one that names no known fact is a new fact.

Health, finances, a precise home address, intimate relationships, and other sensitive personal information are saved only when the user's own message explicitly asks Lorca to remember that fact. The model marks such a proposal `sensitive` and supplies `consent_quote`; the gate requires that quote to equal one complete message in the current turn, not a fragment and not pieces joined from two messages. The structured `sensitive` choice records the model's reading instead of a keyword list deciding what is private. If the model cannot tell whether a fact is sensitive or where it belongs, it saves nothing.

A run adds at most eight new facts, and new facts about the work no more than a quarter of what `MEMORY.md` already holds (at least one); facts about the person and supersedes are held back only by the eight, so a new bot learns who the user is from its first chat. Each run is recorded under `memory/<bot id>/capture/` with the lines it added, the destination of each (`added_targets`, with `profile` kept for older readers), the entries it superseded and which file held each of them, and what was refused; where each chat was last read is kept in `memory/capture.json`. New records name no source chat, chat id, or quote. Older records still parse, but the apps project neither their source chat nor their quote. `memory_capture.list` returns every batch newest first and `memory_capture.undo` reverses any batch that is not already undone; undoing removes each line from the file recorded for it, records it as forgotten so it is not learned again, and restores a replaced entry to the file it came from. A run that changed something says so in the chat, quietly and once, in a line that names up to three facts, a changed one with the fact it replaced, and where to undo it. A fact the reply gives a day for stops being true after that day: the read keeps it in `memory/<bot id>/expiring.json` under the fact's key, and a fact that replaces it takes the day away. Only the bot's memory carries deadlines; a fact about the person goes to the profile, which the [housekeeping](#housekeeping) does not tidy. Every save and refusal goes to the bot's [memory trace](#the-memory-trace); a sensitive fact and its quote are never written there. `LORCA_MEMORY_CAPTURE=0` turns it off. A read waits while a turn is in flight in that chat and while an earlier read of it is still running. The call runs under the DM's [limits](budgets.md) as one of its turns would and its usage counts toward them; when the limits refuse it, the same messages are read once they allow it. A failure is retried up to three times before the chat waits for its next message.

## The user's profile

Every bot on a Runner reads the same `~/.lorca/memory/profile/PROFILE.md` (`crates/cli/src/profile.rs`): who the user is, how they like to be spoken to, and facts that hold in every chat, so a second bot does not have to learn them again. Bots change it only through `profile_update`, with the same four actions as `memory_update` under the same gate and scrubber; an addition that would take it past 8 KB is refused, so the profile stays whole. It rides the note after the transcript under a 120-line / 8 KB budget, framed as information about the person rather than instructions, and the system prompt only says what it is and how to add to it.

The user edits it from a bot's inspector (About you) or with `lorca profile edit` (stdin or a file, with `--expect <hash>` to refuse a stale write), and `lorca profile show` prints it with its budget. `profile` / `profile.write` are the app API and take a `runner_id`, this Runner by default; for another Runner the CLI asks it with the sealed `profile.read` / `profile.write` requests. The profile is the account's: what one Runner's `PROFILE.md` learns reaches every other Runner's (`crates/cli/src/profile_sync.rs`). It rides the roster blob ([Protocols](protocols.md#cli--relay)), which the account key encrypts and the relay already carries, as its `profile` field merged entry by entry, so the relay stores nothing new. The account keeps one entry per fact, keyed by the fact without its bullet, date, source, case, or extra spaces, each with when it last changed; the later change wins, and on the same second the same entry wins on every Device. A fact that left a profile (removed, superseded, or deleted in an editor) stays as a gone entry, so a Runner that has not heard of it does not bring it back, and one removed with `remove` is gone as forgotten, so every Runner's write gate refuses it. Every Device keeps the entries in `memory/profile/account.json`, which unpairing deletes; a Runner also keeps which facts its file held when the two last matched. Before each roster it sends and after each one it takes, a Runner folds what changed in its file since then into the entries (a fact the file gained was written here; one it lost left here), then makes the file say what the entries say: a live entry it lacks is added at its end and a gone one's line taken out, its order and its struck-through history left as they are. A Runner's first sync only adds its own facts and takes nobody's away. The routine scheduler's half-minute tick sends the roster again when a bot, the capture, or the user changed the file. A phone carries the entries on and writes no file. A CLI older than this sends a roster without the field, which changes nothing, and keeps its own `PROFILE.md` until it is updated.

## Across chats

Two things keep a bot's chats from being islands, after OpenMausBot. Every turn carries a **recent-work brief**, a bracketed note after the transcript: the newest thing the bot said in each of its *other* chats over the last two days, at most ten lines and about 350 tokens, newest first (`- today 09:05 · group "Standup" · you said: "…"`), so a bot in a group knows what it did in its DM an hour ago without the transcript. It stays out of the system prompt, which it would change each time the bot speaks elsewhere, costing the chat its prompt cache. And `recall` searches the memory files and every chat the bot is in by words and by time, naming the chat and the speaker of each hit.

Before a compaction summarizes part of a chat, a silent **memory flush** turn runs over the messages about to be cut, with a prompt to save what is durable and not yet recorded in the right place, and only `memory_update`, `memory_log`, and `profile_update` run; nothing it says reaches the chat, a failure or a two-minute timeout is logged and the compaction goes ahead (`LORCA_MEMORY_FLUSH=0` turns it off). The prompt uses the same routing as a turn and the capture: user profile through `profile_update`, the bot's own durable work through `memory_update`, project context, tasks, and logs for their own kinds, and nothing when the destination is unclear. Its writes pass the same sensitive-consent gate. A compaction of a turn's own context (before the turn, or between its model calls) asks the flush as that turn's next request: the turn's system prompt, tools, every message, and the notes its requests end with, then the prompt naming the message the kept part starts with, so the provider's prompt cache serves the context, and the hooks refuse every tool but those. Any other compaction asks it as a request of its own, with only those tools, over the newest of the history one request may carry. This is what keeps a fact from being lost because it was only ever said in conversation.

## Recalling what bears on a message

`MEMORY.md` opens every turn only up to its budget, and the topic files open only when the bot reads them, so a turn the user's message starts also carries what the bot remembers about that message (`crates/cli/src/memory_index.rs`). When the turn starts, the Runner searches the bot's `MEMORY.md`, its `memory/<topic>.md` files, and the Runner's `PROFILE.md` for the message's words and puts the best six lines, each cut to 200 characters and named by its file, in a note after the transcript, after the recent-work brief (`[What you remember that bears on the user's message …]`). A line the loaded part of `MEMORY.md` already shows stays out. The search runs once, when the turn starts, so every request of the turn carries the same note. A routine's run, an event, a teammate's message, and a group's turn that no message of the user's started search nothing.

The search is SQLite's FTS5 ranked by BM25, with no embeddings, in `memory/index.sqlite`. Its rows are each bot's lines and the profile's, without the entries a supersede struck through; a search reads only the asking bot's rows and the profile's, so one bot never finds another's memory. The markdown files stay the only record. Before each search the index compares the sizes and change times of the bot's files with those it last read, and makes the bot's rows again from the files when they differ, so whatever wrote a file (`memory_update`, the capture, an app's editor, a template) is found from the next turn; deleting the index loses nothing. Chinese, Japanese, and Korean are written without spaces, so each of their characters is a word in the index and a query matches any two of them side by side: 下周去杭州 finds 用户住在杭州 by 杭州. Every query term is quoted, so FTS5's own syntax in a message is plain text, and words shorter than three letters stay out of the query, since they match nearly every line.

## The memory trace

Each bot's Runner keeps what its memory did, one JSON line per event in `memory/<bot id>/trace/YYYY-MM-DD.jsonl`, the newest 14 days of them (`crates/cli/src/memory_trace.rs`): `recalled`, the user's message and the lines its turn was given, or none; `saved`, a fact `memory_update`, `profile_update`, or the [capture](#learning-from-a-quiet-chat) wrote and the file it went to; and `refused`, a fact the write gate or the capture refused and why. A duplicate changes nothing and leaves nothing. Text is scrubbed of credentials as memory is and cut to 240 characters. `memory.read` answers with the newest 50 events as `trace`, which only Lorca Dev's desktop app shows ([In the apps](#in-the-apps)). Templates read only `MEMORY.md` and the topic files, so the trace never leaves the Runner.

## Housekeeping

Once a day, while none of its turns runs, each bot's Runner tidies its `MEMORY.md` so what opens every turn stays what the bot uses (`crates/cli/src/memory_tidy.rs`). It moves lines and never rewrites or forgets one, and no model call runs, so it costs nothing:

- the struck-through history of supersedes goes to `memory/history.md`, where the write gate still finds what a supersede replaced;
- once the file holds three quarters of what loads every turn, up to 20 entries saved 60 days ago or more that no user's message found in that time go to `memory/archive.md`. A message finds an entry when its [recall](#recalling-what-bears-on-a-message) matched it, given to the turn or already in the loaded part, as the bot's [memory trace](#the-memory-trace) records.

A fact with a deadline goes the day after it, whether or not the file is near its budget, and one whose fact was already replaced or removed has its deadline dropped. Both destinations are topic files, so `recall` and a turn's recall note still find what moved. Each pass is a run under `memory/<bot id>/tidy/` with exactly what it moved, and `memory_tidy.undo` puts those lines back at the end of `MEMORY.md`, with the deadlines they carried, and takes them out of the topic files; a pass that would write over a change made in between is refused and moves nothing. Only `MEMORY.md` is tidied: the profile is the account's and syncs to every Device, so nothing changes it in the background. `LORCA_MEMORY_TIDY=0` turns it off.

## In the apps

The desktop app's DM inspector shows the bot's memory (`bots.memory`): the index against its load budget, an editor (`bots.memory.write`, refused with the bot's current text when the file changed under the editor, then Reload or Overwrite), a Show button for the folder, in Lorca Dev a Trace row that opens the bot's [memory trace](#the-memory-trace) newest first with Reload (`sheet_memory_trace.go`), and every automatic capture batch newest first. Each batch shows its time, its facts, whether each fact went to `PROFILE.md` or `MEMORY.md`, and whether it was undone; Undo… lists an active batch's facts and forgets them on the user's word. No batch shows a source chat, chat id, or quote. A Tidied row says what the newest [housekeeping](#housekeeping) pass moved, and Undo… puts it back. Its own About you section edits the profile on the bot's Runner, with the same Reload or Overwrite on a conflict. The Bot tab's This chat section has Prompt, which shows what the bot's next turn sends in that chat (`bots.prompt`, `lorca prompt <bot>`): each section of the system prompt with its size, then the notes after the transcript, with Copy. For a bot on another Runner the CLI asks that Runner through the relay (a `request` / `response` pair, see [Protocols](protocols.md)), so the same rows work; only the folder cannot be opened, and an offline Runner shows as such with a Retry. The phone's DM Details has a Memory row that opens the same pieces as screens: MEMORY.md with its line count, opening an editor with the load gauge and Save, which on a conflict offers Reload or Overwrite with mine; the topic files; every automatic capture batch with its facts, destinations, and per-batch Undo…; the newest housekeeping pass, Tidied, with Undo…; About You, the Runner's profile in the same editor; and Prompt, the next turn's sections that expand on tap, the notes after the transcript, and Copy. The screen reloads each time it comes back into view, so an edit made elsewhere shows.
