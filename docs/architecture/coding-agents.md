# Coding agents

A bot hands a coding job to Claude Code, Codex, or another agent that speaks the Agent Client Protocol (ACP) on its Runner and supervises it: the agent works on its own in a git worktree, the bot reads its transcript, sends it follow-ups and stops it, and hears when it is done, stalls, or exits, with the outputs Lorca published from its work. `crates/cli/src/coding/` holds it: `tool.rs` the bot's tool and the review of a start, `mod.rs` the agents on the Runner and their cards, `acp.rs` the one driver every agent runs under, and `workspace.rs`, `proof.rs`, `process.rs`, and `lines.rs` the folder, the outputs, the process, and the transcript. Every agent is driven through one interface (`driver::Driver`): a message, the commands it offers, and Stop; its supervisor (`supervise`) turns what it reports into the card, the transcript, and the bot's turns.

## Starting one

`coding_agent { action: "start", prompt, agent?, folder?, worktree?, secrets?, plan?, model?, effort? }` starts one and answers at once with its id (`agent-3f9a2c1d`), which the bot keeps across turns. `agent` is one of the agents below ([Agents over ACP](#agents-over-acp)); without it the Runner's Claude Code, else its Codex, found on the login shell's `PATH` as a terminal would find it. Neither installed is an error that says to install one, and a named agent that is not installed says which is.

`folder` is where the job is: absolute, `~/…`, or relative to the bot's working directory, which it defaults to. In a git repository the agent never works in the checkout itself but in a worktree of its own under Lorca's folder, `worktrees/<repository>-<hash>/<name>`, on a branch of that name made from the repository's current commit: a new one named after the prompt's first words, or the one `worktree` names, which a later start in the same repository works in again. A folder that is not a repository is worked in as it is. The agent gets the bot's prompt, then where it works, and to give a pull request's link in its last message.

The start needs the bot's Access to Shell commands ([Bot permissions](bot-permissions.md)), and passes [Auto-review](auto-review.md) as a command does, on the card of the call (below): the review reads what starts, where, and the prompt, and proposes a rule for Always allow. A held start goes back to the bot with why, its card `denied` and `held`; after three holds in a row the card asks the user. A routine's or an event's turn, which nobody watches, is refused when the review holds or asks. An agent an event started, a channel's message among them, keeps the owner's task for that event (`Record.event`, without the event's text), and the review weighs its every later action against that task, as it does the turn's own: what someone outside wrote never authorizes it.

`plan`, `model`, and `effort` set the session as it opens, by what the agent's `configOptions` offer (`requested`): `plan` is the setting that has a plan mode, `model` and `effort` those of the `model` and `thought_level` categories. A value is found by its id or its name in any case, or by being the only one that holds the words; one the agent cannot take fails the start with what it offers (“Claude Code has no effort “extreme”. It offers: Low (low), High (high).”), so the bot asks again or leaves it out. In plan mode the agent's request to leave it (`switch_mode`) is the “Approve plan” tool question, decided like any other (Auto-review, then the card), and the agent goes on in its own mode once it is approved. The bot cannot choose a mode itself: some switch off the questions Lorca answers.

`secrets` names the bot's own saved command secrets ([Secret requests](secrets.md)) the job needs, such as `NPM_TOKEN` to publish a package; any other name fails the start, saying to ask for it with `request_secret`. The agent has each as `$NAME` in its environment, looked up again whenever its process starts, and its brief says to use them only with the service each is for. The start's review is told which it holds, and so is the review of every command it runs, none of which takes the fast paths below. Saved values never reach an agent otherwise: a value in the prompt or a follow-up goes as its placeholder, which is not filled.

## Agents over ACP

Every agent speaks the Agent Client Protocol and runs under one driver (`acp.rs`, on the official `agent-client-protocol` crate, pinned with its schema) as a process of its own: a process group (a job object on Windows) with the login shell's environment, less the markers a Claude Code session leaves for its children, plus the secrets it was given. What differs between agents is one table (`SPECS`). `claude` and `codex` run adapters pinned to a version, `npx -y @agentclientprotocol/claude-agent-acp@0.94.0` and `@agentclientprotocol/codex-acp@2.2.2`, that wrap the user's own CLI (`CLAUDE_CODE_EXECUTABLE`, `CODEX_PATH`), so its install and sign-in are the ones used; they need `npx` too. `pi` runs `pi-acp@0.0.34`, which drives the user's `pi` (`PI_ACP_PI_COMMAND`) in its RPC mode; pi asks before nothing, so none of its commands or edits reaches Lorca to decide. `gemini`, `opencode`, `kimi`, `copilot`, `cursor`, and `kiro` run their own ACP mode. All but `claude` and `codex` start only when named. A CLI that is not installed is not offered.

Lorca names itself in the handshake (`clientInfo` `lorca`) and declares no `fs` or `terminal` capability, so the agent runs its own tools; it declares `elicitation.form` ([A coding agent's questions](questions.md#a-coding-agents-questions)), `session.notices` and `session.compaction`, so the agent's notices and context compactions come as updates of their own rather than words in what it says, and, in `_meta`, `terminal_output_delta`, the convention Zed reads, under which a command's tool call carries what its terminal wrote in chunks (`terminal_info`, `terminal_output_delta` or `terminal_output`, `terminal_exit`) instead of beside its result. It resumes the session when it has one (`session/resume`, without its history, where the agent offers it; else `session/load`, whose replayed history it passes over), else opens a new one, and sets the session's mode to the one under which the agent asks before it acts (`default` for Claude Code, `workspace-write` for Codex), then the settings the last run ended with (`Record.config`; Codex forgets its model and mode when a session loads). One prompt is in flight. A message sent meanwhile waits and goes when the turn ends; an `interrupt` cancels the turn (`session/cancel`) and goes first. The agent's permission requests become the approvals above by their kind (`execute` a command; `edit`, `delete`, and `move` files; `switch_mode` a plan; any other a tool), answered with the one choice for this once or the refusal, never one that also stops it asking again; a request with neither is declined. Codex ends its whole turn when a request is refused, which the bot hears as an error. A turn that ends with nothing said or done, or cancelled, refused, or out of tokens or steps, is an error for the bot, not "done". A mode the agent changes itself (`current_mode_update`, `config_option_update`), as when a plan is approved, reaches the card and the settings a resumed session gets back. A setting not answered in 20 seconds is given up, and dropping the request sends `$/cancel_request` for it (the SDK does). Stopping an agent closes its session first where the agent offers `session/close`, three seconds at most, so it cancels its work and keeps its session whole, then stops its process. Updates reach the transcript (messages, tool calls with their output, edits, and results, plans); one Lorca does not know is ignored. A command the user's own Claude Code settings allow does not ask, so Lorca does not see it.

The card shows what the session says of itself (`settings`, a line under the status): its model, how hard it thinks, and its mode, each as the agent titles it and names its value (`configOptions`, kept up to date by `config_option_update`, or the older `modes` and `models` an agent may say instead), then its context in use and its cost when it reports them (`usage_update`). They are the agent's own words, so they are not translated.

A handshake not answered in 30 seconds (240 for an adapter's first download) says the agent's version may be too old to speak ACP, with its last words on stderr; a session that needs a sign-in says to sign in once in a terminal.

## What it may do

Every command an agent runs passes the bot's Access as it stands, then Auto-review as the bot's own commands do (`approve`): a command the parser proves only reads, one that stays in Lorca's own folders (its worktree is in one), or one that only makes, copies, and moves files in its worktree, runs at once, unless the agent holds secrets; the review model judges anything else, a push or a deploy, against the request behind the turn that started the agent, with the git state of what a command would discard. Files it changes outside its folder, and its other tools that would ask (a web fetch, an MCP tool), go to the review too. What the review allows runs. What it holds goes back to the agent as a denial that says why (`review::agent_note`): it goes on another way, or stops and names what it needed, so the bot can ask the user. After three holds in a row, what the review holds goes on the agent's card as a question, `command`, with why and the rule Always allow adds, answered from any Device with `chats.permission`, as a command's card is. It waits ten minutes, and a message from the user in the chat dismisses it. An agent told no hears why and goes on without it.

## Its questions

Lorca declares the ACP `elicitation.form` capability, so an agent can ask the user (Claude Code's AskUserQuestion; without the capability its adapter removes the tool and the agent guesses). A form arrives as `elicitation/create` with a message and a schema (`form_of`): a menu (`oneOf`, `anyOf`, or `enum`, each pick with its title and description), several picks (an array of those), yes or no, text, or a number. A free-text field named after a menu's (`question_0_custom` after `question_0`) is that menu's own words, not a field of its own. A link-style (`url`) request is declined.

The question is a card of its own in the chat, which the user answers from any Device or the bot answers for them: [A coding agent's questions](questions.md#a-coding-agents-questions).

## Following it

What an agent says, runs, shows, and asks, and what it is sent, has the Runner's saved secrets replaced by their placeholders before it reaches its transcript, its log, its card, the review, or the bot (`without_secrets`), as a tool's result does: an agent may print a value its environment or a file holds.

The bot reads the transcript as text: `> ` and what the agent was sent, what it said, each tool it used (`● git status --short`, `● Terminal(git status --short)`, `● Edit(src/login.rs)`, paths from its folder), the first lines of what came back (`  ⎿ …`, a command's output without its colors), and a plan as `● Plan` with its steps. A call is shown once it can say what it acts on, or when it ends. The last 5,000 lines stay in memory and every line in `agents/<id>.log` (0600).

The apps read it as entries (`entries.rs`), which the driver puts under keys of its own and changes as they go: `sent` and `said` text (a message grows as it streams, and a new `messageId` starts another entry and is the one the bot hears as its last), `thought` text (what it thinks, `agent_thought_chunk`, for the apps only), a `tool` with its title, its own name where the agent gives one (`Bash`, which the bot's line reads as `● Bash(git status)`), what it acts on, its kind and status, its command's output as its terminal wrote it, its exit code, its edits as diffs (each changed line with three around it, `+`, `-`, or ` `, `@@` between parts, from the edit's text before and after), and what else it gave back; a `plan` with its steps; a `notice` of the agent's with its `level` (`info`, `warning`, `error`; the bot reads `⎿ Warning: …`); a `compaction`, one entry for each time it compacted its context, with its `status` and the summary it kept; and a `note` of Lorca's (a refusal, an answer, a setting changed, how a turn ended). The title the agent gives its session (`session_info_update`) goes on the card as `title`. Each has its place (`seq`) and the change it was last part of (`rev`): `coding.transcript { since }` answers the entries changed after `since` with `rev` and the first entry kept (`first`), so an app asks every two seconds for what changed rather than for all of it. Output keeps only its color and style sequences (`terminal_text`): any other escape sequence (a clipboard write, a link, a title) and control character is dropped before it is kept, and it is kept from its end, 64 KiB of it. The last 1,000 entries stay in memory, with the Runner's saved secrets as their placeholders, and in `agents/<id>.entries.json` (0600) once the agent is done or gone. An agent from before entries starts with its text as one `log` entry.

- `read { id, lines? }` answers what is new since the bot last read, up to its last 200 lines, or its last `lines`, and how it stands.
- `send { id, message, interrupt? }` gives it a follow-up, which it takes up when its turn ends; `interrupt` cancels the turn first (`session/cancel`). An agent whose process is gone, because it was done and idle for an hour or Lorca restarted, starts again on its session (`session/resume`, else `session/load`).
- `answer { id, answers | choice | text | decline }` answers or declines the question it asks in the chat ([A coding agent's questions](questions.md#a-coding-agents-questions)).
- `set { id, model?, effort? }` changes the model or how hard a running agent thinks, with its conversation kept (`session/set_config_option`, found and refused as `start` does it). The change reaches the settings a resumed session gets again, and the transcript says `● Set model to Opus`. A turn under way is not waited for; an agent that takes the change at once uses it from its next step. An ended agent keeps its settings, and a mode cannot be set at all.
- `stop { id }` ends it; `list` answers the bot's agents in the chat; `commands { id }` lists the slash commands and skills a running agent offers, which the bot runs by sending `/name` (Codex: `$name`).

An agent is `starting`, `working`, or `idle` (done with what it was asked, waiting for a follow-up), and `asking` while a question waits; once it ended `exited`, `failed`, or `stopped`. One working with nothing new for ten minutes is `stalled`; a spinner's timer ticking is not news.

## When it is done

When an agent goes idle after working, Lorca publishes what changed in its work as [outputs](outputs.md) of the bot's (`proof::publish`): its diff against the commit it started from (commits, edits not committed yet, and new files, up to 2 MiB) as `<branch>.diff`, a saved secret in it as its placeholder, a new version whenever it changed; the pull request or merge request its transcript names, once, as a link. Then the bot gets a turn of its own, an `agent` job, once no turn runs in the chat, unless a turn read the agent meanwhile: it opens with what the agent said and each output's name, message, output id, and version, which the bot cites as [task evidence](tasks.md). A stalled agent, one that exited by itself, and one that asks a question wake the bot the same way, with its last lines or its question.

While an agent works, its run time counts toward the limits of the turn that gave it the work, the start or a follow-up ([Budgets](budgets.md)): the turn's scopes hold a run (`BudgetContext::hold`) until the agent is idle, and a time limit reached stops it.

## Stop, quitting, and restarts

Stop in the chat stops every coding agent there, as it does the bot's commands, here or on the Runner when the bot's turn is cancelled there ([Stop](stopping.md)). A start under way when the turn is stopped finishes in a task of its own (`start_unless_stopped`) and stops its agent as soon as it runs, so Stop never leaves one running unfollowed. The card's Stop (`coding.stop`) reaches it from any Device. Deleting the chat or the bot stops and forgets its agents.

`agents/agents.json` (0600) keeps every agent's record: its chat, bot, card, kind, session and settings, folder, branch, state, and what it published. Quitting stops the agents, whose cards read "Stopped when Lorca quit" unless they were done. One that was starting, working, or asking when Lorca quit, in an orderly quit (`shutdown`) or one that did not run (`load` finds the saved state), keeps `News::Interrupted`; on the next start `wake_unheard` gives its bot a turn that says it was cut off and how to start it again, as it does for any news a quit left unheard. On the next start their handles still work: a done one starts again on a follow-up.

The bot's system prompt tells it to say in a message what it started once `coding_agent` starts an agent, and to tell the user how it went each time it hears the agent is done, stalled, ended, or cut off, so a turn does not end on the tool call. An ended agent is forgotten a month later. An update of the CLI waits while an agent is at work.

## The card

How an agent stands is read off its card once, in the CLI (`AgentRun::summarize`, on every card it stores and sends the apps, one from before included): its `tone` (`ask` while it needs the user or went quiet while working, `busy` while it is checked, starts, or works, `done` when idle, `fail`, or `quiet` once it ended otherwise), `busy` (it starts or works and asks nothing, so its dot breathes and its time ticks), `context` (the tokens used of its window, from its `Context` setting), and `now` (its last tool's line, without the mark). The apps tint by the tone and read the rest; they keep no rules of their own for it.

The `coding_agent` row that started an agent carries its card from the start, `Body::Tool.agent`: `{ id, kind, name?, settings?: [{ name, value }], controls?: [{ what: model | effort, name, value, choices: [{ value, name }] }], task, folder, branch?, state, stalled, held, question?: { kind: start | command, command?, reason?, rule? }, asking?, title?, output?, outcome?, pull_request?, device?, started_at? }`, with `checking` while Auto-review judges the start. `output` is its last 20 lines. The card keeps its first place in the relay's log however often it changes, a question on it counts as unread and pushes as a command's does ([Notifications](notifications.md)), and it stays after the agent ended. `coding.transcript` (its last 2,000 lines), `coding.stop`, and `coding.answer` go to the bot's Runner from any Device as sealed requests.

Every app shows the card in the chat: the agent's name, with Stop at the end of the line while it runs; what it was asked; how it stands in a word (Starting, Working, Quiet, Done, Ended, Failed, Stopped) with its branch; and while it works its last lines. Before it starts the title is the bot's ("Developer wants to start Claude Code on Workbench") with Allow once, Always allow, and Deny; for a command, "Claude Code wants to run a command" with the command in a code block that opens it whole. While the agent's own question waits, the status reads "Asks you in the chat".

The question's card is drawn as [Questions](questions.md#a-coding-agents-questions) describes. A click on what it works on opens its transcript, which asks for what changed every two seconds on the Runner and five elsewhere, and keeps to its end unless the user scrolled up.

The desktop draws every agent surface from one kit (`desktop/agentkit.go`): the agent's mark (`agentmarks.go`, Claude's spark, OpenAI's knot for Codex, a prompt for the rest) on a tile in its color; how it stands as a pill in its state's tint, whose dot breathes while it works, with how long it has worked (`started_at`); a console, a dark well in both appearances with the last lines, each tool's line bright and a spinner on the one it runs now; and callouts for what it asks and how it failed. The card (`desktop/agents.go`) is the tile, the name over its branch and Runner, the pill, and Stop; what it was asked; while it works, the console; its session as a strip of cells, the model (without a gateway's prefix and context hints), the effort, and the mode, each a label over its value and a pop-up where it can change now (`controls`, `coding.set { chat_id, message_id, what, value }`), over a meter of its context with its share and what it cost; the pull request it opened; and a footer with when it started and a link to the transcript. The transcript (`desktop/agenttranscript.go`) is a timeline: each turn opens with what the bot sent, in the accent, and each entry sits on a rail with a node of its own, the agent's tile for what it said (Markdown), a tool's state (a spinner, a mark of its kind, a red cross), a thought, the plan, a compaction, or a notice in its level's tint. A tool's line shows its edits' added and removed lines and a failed command's exit code, and a click opens or closes it; a tool that runs, one that failed, and the last one are open. A thought and a compaction open to their text, and the plan counts its steps done. An open command's output is on MyGo's terminal plugin (`desktop/agentterm.go`), the latest six at most, each a read-only terminal with no program that is fed what the output adds after what it has, its colors only (`terminalBytes` drops the rest again), so nothing an agent's command printed drives the emulator; an older one, and any where the plugin's library cannot load, is plain text. An edit is its diff, added lines green and removed ones red. The phone draws the same kit with native views (`src/ui/agentKit.tsx`, what it reads off the card in `src/core/agentKit.ts`): the card is `AgentRow` in `src/ui/transcript.tsx`, and a tap on it opens `app/agent/[id].tsx`, a sheet that is the phone's full view: the header with Stop; what the desktop's column beside the transcript holds, stacked above it; the timeline of the same entries (`src/core/agentEntries.ts`, read again every five seconds while the sheet is up, where an entry at the revision it holds keeps its row as drawn), a command's output in its colors (`outputSpans`, which keeps `ESC [ … m` only); and what the agent asks under it.

On the desktop every agent at work also has a window of its own that floats over whatever is on screen, a chat or not (`desktop/agentpip.go`; `Store.RunningAgents` lists them from the latest 80 messages of each chat). It comes up when the agent starts working, the next ones a little off the first, and goes when the agent is done or stopped. Its title drags it, kept inside the app window: the tile, the name, the pill, Full Screen, and Close; its body is the card, smaller: what it works on, its console, its model and effort with Stop, and what it asks, answered there as on the card, with a hairline along its foot of how full its context is. Close keeps it away until the agent works again. A click on its body, or Full Screen, fills the app window with the agent: a header with its tile, its name over its session's title, its pill, and Stop; its transcript in a reading column 760 wide, with its question's card under it; and a column beside it of what it works on, its workspace, its session, and its plan with its steps done; Escape or the button in the corner brings the window back. On the phone the agents at work in every chat sit over the composer as small cards on its floating glass (`src/ui/RunningAgents.tsx`), the latest started first and sideways when there are several: the tile, the name, the pill, what it does now or what it asks, Stop, Close, and the context hairline; a tap opens its sheet from whichever chat is open. While the agent runs, the card and the full view show its model and effort as pop-ups (menus on the phone) (`controls`, which the driver reads from the session's `configOptions`) that ask the Runner to change them (`coding.set { chat_id, message_id, what, value }`); a card that asks shows none.
