# Bots and Memory

## Bot profiles

A bot's look is an SF Symbol (`symbol_name`) on an accent gradient (`accent`), or a profile image of the user's own: `avatar` is an attachment record whose bytes travel as an encrypted `file` blob, the same way a message attachment does, and every Device shows the image in place of the symbol once it has fetched it. Clicking a bot's avatar in the macOS inspector opens the Look sheet. The macOS Profile card keeps Name trailing-aligned and opens Description in its own editing sheet. On the phone, tapping the avatar in Details slides the Look screen in inside the same form sheet (`app/chat-info` has its own stack); Name is trailing-aligned there too, and the Description row pushes a full editor. Details also has native Provider, Model, and Thinking menus under Runs with; a provider change clears the other two to that provider's defaults, and Thinking offers only the levels the model takes (see [Providers](providers.md)). `bots.update` carries all of these changes, including `symbol_name`, `accent`, and `avatar` (a `{ path, … }` file to store and upload, or `null` to remove).

A new name or description, or a finished setup, applies from the bot's next step, in a turn under way too. Between steps the turn compares the bot's name, description, and setup with the bot as it stands (`TurnHooks::refresh_profile`), so a change in its details, by `edit_bot` or `finish_setup`, or synced from another Device is caught, and makes its system prompt again; a turn that finishes the setup goes on with the usual tools. Provider, model, thinking, and working directory apply from the next turn, since the turn's provider and tools are made with them. `App::update_bot` also leaves a notice in the bot's DM (`model::profile_notice`, its id starting `profile-`): "Set up as Name. …", "Name was renamed New.", "Name's description changed."; a new look, Access, or model leaves none. Without it the bot's own earlier words about itself, still in the transcript, outweigh its system prompt. Its turns read the latest notice as the profile as it stands, its name and description (up to 2,000 characters) with what the chat said about it before marked out of date, and earlier ones as marks of a change (`turns::profile_note`); a turn under way reads the same note the step after the change.

## A bot on another Runner

Creating a bot for Runner B from Device A: A writes an encrypted bot profile into the roster (paired Devices can read it) and pins B’s machine id. Bot create rejects a target whose `os` is not desktop. Turns are job envelopes addressed to B. B decrypts the job, runs the loop with the account’s provider credentials, and uploads encrypted replies.

If B is offline, the envelope waits on the relay until B fetches it. The UI infers that from decrypted roster state. A turn for a provider the account has not connected ends with a notice in the chat that says to connect it in Settings.

## The lead bot

A new identity starts with one bot, **Chef**, a chief of staff on the first Runner: an ordinary bot whose description has it route each request to the teammate whose job it is with `message_bot`, pull their results together, propose a new one for `create_bot` when none fits, and do the work itself only when no teammate's job covers it. Nothing about it is privileged; rename or delete it like any bot.

Every bot's system prompt names its team (`turns::team_prompt`): each other bot as `- Name (id …): the first 60 characters of its description's first line`, at most 20 bots, leaving out the members a group lists already. The whole description, the plugins its Access limits it to, its Runner, whether that is online, and its model are in `list_teammates`, so the roster changes only when a bot is added, renamed, or given a new job, and the chat keeps its prompt cache. The routing rules follow the team, except in an unattended turn (a routine's run or an event), which has the roster and a line about `message_bot` alone, no rules for the user's requests, and no `create_bot`, `edit_bot`, `create_group`, `edit_group`, or `recommend_plugins` among its tools: a part that falls in a teammate's job goes to that teammate even when the bot could do it, a request spanning several jobs is split with one teammate per part, and the bot does the work itself only when it is its own job, no teammate's covers it, or a line answers it. It tells the user in one line who took which part and checks the results against what it asked for.

A chat has a `kind`. A DM is one bot and never gains or loses members; there is one DM per bot. A group holds one to six bots, can add or remove them after creation, and has an `owner_bot_id` (the bot holding the work, marked as the owner in every member's system prompt; defaults to the first member, and moves to the first remaining one when the owner leaves). `chats.set_owner` changes it: in the macOS and Windows/Linux inspectors the owner's row reads Owner, and a click or right-click on a member of a group with several offers Make Owner beside Remove from Chat; on the phone, tapping a member in Details makes it the owner; `lorca chats set-owner <group> <bot>` does it from a terminal. A group may also carry a `description`, what it is for in the user's words, which every member's system prompt gives below the member list; `chats.set_description` changes it, and a DM has none, since its bot's own description says what it is for. The macOS and Windows/Linux inspectors show a group's Name and Description in a Group section (Description's Edit… opens an editing sheet), and the phone's Group Info has the same two rows, Description pushing a full editor.

A group comes from the + button's New Group Chat (desktop sheet, phone screen: bots, a name, and what it is for; the first bot picked owns the work) or from a bot: `create_group` and `edit_group` ([Tools](tools.md)) make and change one through the same `App` methods as `chats.create`, `chats.add_bot`, `chats.remove_bot`, and `chats.set_owner`. The system prompt tells every bot to make a group when the user asks for one or a job needs several teammates working where the user can watch, and to keep a single piece of work for one teammate a `message_bot`. A member's `@Name` of another member reads in that member's color, bold, inside its message (`SplitMentions`); the phone puts a quiet "→ ◉ Writer" line under the bubble instead. Both read the text and the group's members, and leave out a name two bots share.

Deleting a bot removes its DM and routines and removes it from every group. A group with other bots keeps its transcript and moves ownership when needed; a group whose last bot was deleted is removed. The macOS sidebar treats Delete on a DM as this bot deletion and says so in its confirmation sheet. Deleting a group removes only that chat.

Who answers, after Grok Bot's rooms:

- **DM:** its bot, always. An `@Name` is a reference the bot acts on: it calls `message_bot`, which delivers the message into that bot's own DM with the user, where that bot answers (and can message back).
- **Mentions:** picking a bot from the composer's `@` menu records its id, and `chats.send` carries the picks as `mentions`. The CLI keeps the picks whose `@Name` is still in the text, adds any other `@Name` that only one bot answers to, and stores the ids on the message (`Body::Text.mentions`). A bot reads the first `@Name` of each as `@Name (id bot-1a2b3c4d)`, so a name two bots share still says which one the user meant.
- **Replies:** a user message can answer an earlier text message, the user's or a bot's. `chats.send` carries its id as `reply_to`, and the CLI keeps a quote with the reply (`Body::Text.reply_to`: the message's id, its author, and its words as plain text on one line, at most 280 characters), so every Device shows it where the original has not loaded. A bot reads the quote ahead of the user's words (`[Replying to your message: "…"]`, or Scout's message, or their earlier message), and in a group the bot whose message is answered takes its turn right after the ones the message mentions. The macOS and Windows/Linux apps offer Reply on a bubble's right-click, the phone on a swipe of the bubble to the right (as in Messages and Google Messages; a drag that starts elsewhere or at the left edge stays the system's back gesture, and the drag runs on the UI thread); the composer shows "Replying to Name" and the quote until the message goes, Escape or its button drops it, and the sent bubble carries the quote above it, which scrolls to the original and pulses it when clicked.
- **Attachments:** a user message can carry files. Their bytes travel as `file` blobs; before a turn the Runner fetches any it lacks (`files::prefetch`), copies each into the bot's workspace at `attachments/<attachment id>/<name>` (a stable path, so every turn names the same file), and the transcript's user message gets a line per file naming that path, plus the pixels as an image content part made one a model takes (`files::inline_image`, through `lorca_agent::images`: converted, turned upright, or scaled down to fit 2000×2000, with a note; a HEIC converts on a Mac), else a line saying why not. It is made once, before the turn that first shows it (`files::make_images`), and kept beside the attachment as `<id>.inline.json`, since every turn builds its messages again. A request carries only the latest 20 images ([providers](../agent/providers.md#before-conversion)), so a long chat's older ones are left out and the bot reads the file again to see one, so a vision-capable model sees it and any model can open it with its tools.
- **Group:** a room exchange (`run_room`). The Device that received the user's message offers every member a turn, one at a time, in chat order with the members the message mentions first. A member's turn is a `room_turn` Job with the whole transcript plus an ephemeral cue (round number, how many messages are new to it); the member replies to the group or answers `PASS`, which never becomes a bubble. A round with at least one reply is followed by another, offered only to members that have heard something new; the exchange ends after a silent round or after the fourth round, which is marked winding down so members add only what is essential. The owner's prompt has it split the work and assign each part with `@Name` to the member whose job it is, do only its own part, and pull the results together; every member does the part the owner assigns it with `@`. A new user message waits for the current member's turn, including its command, to settle; the old room then yields and a replacement room starts with the new mentions first. **Stop** cancels immediately. A member on another Runner gets its job through the relay and reports back with a `job_result` blob (`sent`, `pass`, `error`) sealed to the requesting Device; the room waits up to five minutes for it and skips an offline Runner.
- **Bot to bot:** `message_bot` from any chat to a bot outside it; the contract lands in the target’s DM, with supplied context, expected output and acceptance criteria. Its durable [handoff](handoffs.md) tracks attempts and automatically returns completion or blocker evidence to the requesting chat and bot. `handoffs` inspects outstanding work, follows up or cancels it. Stop on the requesting turn stops it too ([Stop](stopping.md#what-the-turn-handed-off)). Each hop carries `hops`; after eight bot-to-bot hops without a user message the tool refuses, so two bots cannot loop. Members of one group talk to each other in the group. Admitting a request marks both chats: the target's DM reads "Message from ◉ Sender" and the sender's chat "Messaged ◉ Target", a `Body::Handoff` with the id `sent-<trigger message id>` that no room counts as something new to hear and the sender's own turns do not read back.

A bot's profile also carries the user's [Access](bot-permissions.md): the plugins it may use, how far, and which of their tools, and whether it reads or changes files and runs shell commands. The CLI checks it on each call, and a teammate a bot creates gets its creator's current Access.

### A new bot sets itself up

Every new bot that is not from a template starts as **New Bot** and works out the rest with the user in its own DM. The apps' New Bot (the desktop app's New Bot… command, menu item, and buttons; the phone's New Bot in the chat list's menu) asks nothing: it sends `bots.create { setting_up: true, runner_id, provider }`, picking this computer or the first Runner (on the phone the first online one) and the first connected provider, and opens the new DM. A bot asked for a teammate calls `create_bot` at once with what the user said as `brief`, on its own Runner with its own current Access, and does nothing more for it; the new bot gets its own DM and joins no group.

The CLI gives such a bot the name `NEW_BOT_NAME`, no description, and `Bot.setting_up` in the roster, and starts its first turn (`runtime::start_setup`, job kind `setup`) from a `setup-<bot id>` marker: the creator's brief as a "Message from ◉ Chef" marker the new bot reads, else a "New bot" notice. While `setting_up` holds, every turn of the bot has the setup prompt (`turns::setup_prompt`) instead of the usual one and only `ask_user`, `finish_setup`, `search_plugins`, `recommend_plugins`, and `memory_update`. Its setup is usually one turn, since `ask_user` waits for each answer in it; once `finish_setup` clears `setting_up`, the turn's next step has the usual system prompt and tools ([a profile changed mid-turn](runtime.md#the-system-prompt-and-the-turn-brief)). The prompt has it: greet the user and ask one question at a time, with `ask_user` where there are a few likely answers, until its job is clear (what, for whom, with which services or files, how often, what never without asking); propose a name and a description and ask the user to confirm them; call `finish_setup { name, description }`, which saves them with a look for the name and clears `setting_up` (a name another bot has, or the placeholder, is refused); then search the marketplace and call `recommend_plugins` once. It speaks the language the user writes in, and until they write Chinese when the brief, else the user's latest words on this Device, are Chinese (`plugins::review::is_chinese`). Its teammates' prompts list it as still setting up, and `message_bot` refuses it until it is done.

`recommend_plugins { plugins }`, which any bot has, lists plugins by id or name (installed ones also by account name, or a service id for every account of it) and returns at once. It posts a notice of where each stands ("Plugins for Calendar's job: Notes ready. Install or sign in to Google Calendar below whenever you like."), an Install card for each marketplace plugin not installed, and a Sign in card for each one that needs a sign-in, leaving out a card already waiting in the chat (`turns::recommend_plugins`). The Install card (`tool: install`, `arguments.recommended`) waits on no turn: the user's Install installs the plugin from the marketplace whenever they get to it, or takes an install made meanwhile, then puts up its sign-in card or says what setup is left (`mcp::answer_recommended_install`); Deny closes it. A plugin the bot's Access leaves out, installed or as the new account a named-accounts plugin's install would make, gets no card: the notice says to turn it on in the bot's Access, which only the user changes.

`recommend_plugins { plugins }`, which any bot has, lists plugins by id or name (installed ones also by account name, or a service id for every account of it) and returns at once. It posts a notice of where each stands ("Plugins for Calendar's job: Notes ready. Install or sign in to Google Calendar below whenever you like."), an Install card for each marketplace plugin not installed, and a Sign in card for each one that needs a sign-in, leaving out a card already waiting in the chat (`turns::recommend_plugins`). The Install card (`tool: install`, `arguments.recommended`) waits on no turn: the user's Install installs the plugin from the marketplace whenever they get to it, or takes an install made meanwhile, then puts up its sign-in card or says what setup is left (`mcp::answer_recommended_install`); Deny closes it. A plugin the bot's Access leaves out, installed or as the new account a named-accounts plugin's install would make, gets no card: the notice says to turn it on in the bot's Access, which only the user changes.

## Durable work

[Durable tasks](tasks.md) keep goals, ownership, dependencies, next actions, blockers, and completion evidence across turns and chats. The `tasks` tool and the apps' Tasks section read and edit them. A bot with open tasks reads them again on every provider request, including after compaction. A Job references its canonical task id; a group's chat owner and a task's owner are independent.

## Attention

Every bot maintains structured reviews, blockers, commitments and changes through the `attention` tool. Specialists send ordinary reports to the owning coordinator; urgent reports also alert directly. Coordinators publish one brief of decisions and changes, with source links and next actions, and resolve finished attention items. The user picks any bot as coordinator and controls summary and urgent notifications. The [attention subject](attention.md) describes the encrypted projection, source references, tools, API, and app views.

## Routines

A routine is a task a bot runs on a schedule in its direct chat, on its assigned Runner. The roster carries its schedule, timezone, missed-run policy, and check health. See [Routines](routines.md) for scheduling, read-only checks, recovery, and how the apps show them.

A service's events start work in a bot's DM too, through [event subscriptions](event-triggers.md) on its Runner: each runs the subscription's own task, unattended as a routine's run is, and one that targets a routine waits while the routine is paused.

A workflow adds the routines it needs paused, and `routines.set_enabled` keeps one it added off until the user has read the workflow's sample; a routine of the user's that a workflow reuses keeps its own state: [Workflow onboarding](workflows.md).

## Memory

A bot made from a [template](templates.md#import) gets a DM, the template's memories as its `MEMORY.md`, and its routines paused, and runs no turn or routine check; the user turns routines on from the inspector.

Reusable procedures are [skills](skills.md): folders with a `SKILL.md`, a bot's beside its memory in `~/.lorca/workspaces/<bot id>/skills/`, a group's under `~/.lorca/groups/<chat id>/skills/`, and the ones every bot uses under `~/.lorca/skills/`. Every turn lists them, and a bot reads one with `read` when it fits.

Groups also keep [shared project context](project-context.md): a current brief, goals, constraints, decisions, references, and assets with provenance and freshness. Every assigned member receives that group's bounded index and reads full entries with `project_context`. Corrections and source refreshes survive transcript compaction. Selection is the current group id and membership, while each bot retains its own memory below.

Every bot keeps its own long-term memory on its Runner, in Grok Bot's shape of a curated profile over append-only logs, as plain markdown under `~/.lorca/workspaces/<bot id>/` (keyed by id, so a rename or a changed working directory never moves it; `crates/cli/src/memory.rs`):

- `MEMORY.md` is the curated memory. Its first 200 lines or 24 KB, whichever cuts first, open in every turn's system prompt; past that nothing loads, and the prompt tells the bot how much is cut off and asks it to consolidate. The bot writes it only through `memory_update`, one dated entry per call (`- 2026-09-17 · from your chat with the user · the user prefers short replies`), never a whole-file write, so two of its turns cannot clobber each other: `append` adds a fact (an exact duplicate is refused), `replace` rewrites one unique passage, `supersede` strikes the old entry through with a date and adds the new fact so the file shows what changed, `remove` deletes a passage.
- `memory/<topic>.md` files hold longer notes the bot reads with `read` when it needs them; the prompt lists their names.
- `memory/log/YYYY-MM-DD.md` is the bot's diary: what happened, not what is true. The Runner appends one line per finished turn (`- 09:05 · in group "Standup" · said "Sent the three flagged invoices…" · used bash, edit`), and the bot adds events with `memory_log`. Logs are never loaded into a prompt; `recall` finds them.

Every write is atomic and goes through a credential scrubber first (API keys, AWS and GitHub tokens, bearer tokens, JWTs, private key blocks, `password: …` values become `«redacted N chars»`), since memory is bot-authored as often as person-authored.

Two things keep a bot's chats from being islands, after OpenMausBot. Every turn carries a **recent-work brief**, a bracketed note after the transcript: the newest thing the bot said in each of its *other* chats over the last two days, at most ten lines and about 350 tokens, newest first (`- today 09:05 · group "Standup" · you said: "…"`), so a bot in a group knows what it did in its DM an hour ago without the transcript. It stays out of the system prompt, which it would change each time the bot speaks elsewhere, costing the chat its prompt cache. And `recall` searches the memory files and every chat the bot is in by words and by time, naming the chat and the speaker of each hit.

Before a compaction summarizes part of a chat, a silent **memory flush** turn runs over the messages about to be cut, with a prompt to save what is durable and not yet in memory, and only `memory_update` and `memory_log` run; nothing it says reaches the chat, a failure or a two-minute timeout is logged and the compaction goes ahead (`LORCA_MEMORY_FLUSH=0` turns it off). A compaction of a turn's own context (before the turn, or between its model calls) asks the flush as that turn's next request: the turn's system prompt, tools, and every message, then the prompt naming the message the kept part starts with, so the provider's prompt cache serves the context, and the hooks refuse every tool but the two. Any other compaction asks it as a request of its own, with only those two tools, over the newest of the history one request may carry. This is what keeps a fact from being lost because it was only ever said in conversation.

The desktop app's DM inspector shows the bot's memory (`bots.memory`): the index against its load budget, an editor (`bots.memory.write`, refused with the bot's current text when the file changed under the editor, then Reload or Overwrite), and a Show button for the folder. For a bot on another Runner the CLI asks that Runner through the relay (a `request` / `response` pair, see [Protocols](protocols.md)), so the same rows read and edit it; only the folder cannot be opened, and an offline Runner shows as such with a Retry. The phone shows no memory yet.

A routine can have [limits](budgets.md): its runs and checks, scheduled or started by hand, count toward them together. Once it reaches one it stops until the user resumes it from the routine sheet's Limits row, after raising the limit or with the limits granted again in full.

## Workflow feedback

Explicit acceptance, rejection, edited drafts and user feedback have a structured, source-linked path alongside bot memory. Routine and check failures record mechanical outcomes on the assigned Runner. The coordinator proposes revisions of a routine's task or a skill's instructions with evidence and a diff; the user accepts a guarded version or rolls it back. Routine prompt revisions retain the original task in `feedback_authorization_prompt`, which Auto-review reads as action authority. Optional periodic review, neutral ignored-alert handling and sensitive-material exclusions are in [Workflow feedback](feedback.md).
